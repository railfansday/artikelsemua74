📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Core Lightning’s first 26.12 release candidate adds a way to reclaim funds from some pending Bitcoin Lightning payments.

It applies after an operator loses local channel data and a peer closes the channel by posting a transaction to Bitcoin. The tool gives the operator separate ways to reclaim outgoing funds or collect incoming funds, depending on the payment information that survived.

In a recent development, core Lightning published the test build on Nov. 18, and still headed the project’s release list on Nov. 25 as a pre-release.

Industry observers note that bitcoin Optech covered the feature in its Nov. 20 newsletter and revisited it in its Nov. 24 podcast recap. (Related: Industry News: My Journey to a serverless transformers ...)

Core Lightning’s existing recovery process can reclaim the operator’s main channel balance when the peer posts a closing transaction the recovering node has never seen.

The change adds a fresh tool that addresses a separate output: the amount the closing transaction sets aside for a payment that was still pending.

Industry observers note that both recovery paths require a matching output in the closing transaction that remains unspent. For a payment the operator offered, the tool’s manual says the operator needs the payment hash and the expiry. Once the timelock expires, the operator can reclaim those funds. For a payment the peer offered, the operator needs the preimage, the secret that matches the payment hash. The operator’s claim must be confirmed on Bitcoin before the peer reclaims the same output. Once the timelock expires, the peer can take the funds back.

The tool reconstructs the spending conditions for each payment the operator wants to recover and checks them against the closing transaction, and skips payments that are too small to have an output.

It produces signed transactions for the operator to review and broadcast manually.

Core Lightning 26.12rc1 tests recovery after an operator loses channel data and the peer force-closes the channel.

The tool handles pending-payment outputs. The main channel balance has its own recovery path.

The original node secret, channel and payment details, and the peer’s public commitment point are also required. Outputs that are absent or already spent cannot be recovered.

The two paths follow the tagged Core Lightning manual’s rules for payments offered by the operator or the closing peer.

The operator needs the original node secret, the peer’s closing transaction, channel identifiers and key information, and details for each payment they want to recover.

A cooperating peer can supply the public commitment point tied to the closing transaction while keeping its private keys and commitment secrets private.

Core Lightning’s wallet recovery guide describes using the node secret and an emergency channel backup to reclaim the main balance after a peer closes the channel.

It also warns that restoring an outdated database can permanently lose funds, so recovering a pending payment depends on having enough information to reconstruct its particular output.

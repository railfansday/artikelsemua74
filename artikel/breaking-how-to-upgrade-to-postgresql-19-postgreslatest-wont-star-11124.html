If your compose file states image: postgres:latest, then as of November 20 it says PostgreSQL 19. The Docker Hub tag list now has 19.0, 19 and latest on the same line. The image keeps its data under a version-numbered path (/var/lib/postgresql/19/docker), so after the next docker compose pull && docker compose up -d the entrypoint finds your 17 or 18 data somewhere else, prints Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster" and exits. Your data is safe, but your database is down until you upgrade it or pin the old tag.

In a recent development, that's the small problem, because at least it's loud. The bigger one is that the PostgreSQL 19 release notes list 22 items under "Migration to Version 19", and a few of them change query results without raising a single error. Running pg_upgrade is the easy bit. What follows is the breaking changes sorted by how much they hurt, a pre-upgrade check you can paste, the pg_upgrade and Docker steps, and when RDS and Cloud SQL will actually let you upgrade. According to recent reports, I grouped the 22 items by what happens to you, since the release notes don't order them by impact. A few minor ones (the COPY FROM ... WHERE system-column ban, psql's \crosstabview now honoring \pset null, the new password expiration warning, the MD5 login warning) are left out of the table.

The ones I'd worry about are json_array() and the FTS/pg_trgm change, plus fuzzystrmatch if you have non-ASCII names. Most of the rest either fails loudly or shows up on a dashboard, while these hand back different data and nothing errors. If you're on an ICU database with LC_CTYPE set to C, which is a pretty common setup, budget time for the reindex.

Two default changes didn't make it into the Migration section but are worth knowing: log_lock_waits is now on, and default_toast_compression is now lz4 where the build supports it.

The pg_upgrade docs support sources from 9.2 onward, so 17 and 18 are both fine. Always run --check first. It can run while the old server is still up (use a different port for the upcoming one), and if you pass your transfer mode along with it, you get that mode's checks as well.

Sources indicate that the one real argument in the HN thread was about this. lfittl said that for critical production systems it's still good to wait for .1, and in a follow-up pointed to a crash in EXPLAIN (BUFFERS) without ANALYZE when auto_explain is on. It's an edge case, by lfittl's own description, but the fix "will only be in 19.1 in February 2027". They also noted SQL/PGQ was reverted "pretty late (beta4)". Answering the same question, guenthert said to put it in a test environment: "Waiting won't do you any good, if there are load-specific bugs.".

Recent findings suggest that I'm with both of them. Put 19 on staging this week, run the grep above, and fix your configs and dashboards now. Production waits for 19.1. If you're on RDS, AWS has effectively made that decision for you.

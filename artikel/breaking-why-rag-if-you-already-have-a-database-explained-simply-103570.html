Breaking: Why RAG If You Already Have a Database? Explained Simply 🔎

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Your company already keeps its HR policies in a database. An employee types: "Can I carry over my unused holidays to next year?" The answer is sitting right there in a table, and the search box still returns nothing useful.

Recent findings suggest that this post explains why that happens, what RAG (Retrieval-Augmented Generation) adds on top of your database, and when you don't need it at all. You'll see a small before-and-after in Python. (Related: How to generate text: using different decoding methods ...)

A database is a very fast, very literal librarian. Ask for the book with ID 4021 and you get it instantly. Ask for "rows where the text contains carry over" and it checks every row for those exact letters. If the policy says "rolled forward" instead, the librarian shrugs. It isn't being lazy; it was never built to understand language. (Related: Industry News: How to train a new language model from s...)

Here is our running example. The table holds four policy lines:.

The employee says "carry over" and "holidays". The policy says "rolled forward" and "annual leave". Same meaning, zero shared words. Worse, the word "holidays" does appear, but in the wrong row (public holidays).

It has been revealed that you might say: "Postgres has full-text search." It helps. Postgres can reduce words to a base form, so rats matches rat, and it can rank results by relevance. But matching "carry over" to "rolled forward" needs a synonym dictionary that someone writes and maintains by hand. Nobody can list every way a person might phrase a question.

That gap is what RAG fills. Three terms first:.

RAG = Retrieve the most relevant text by meaning, Augment (add) it to the question, and let the LLM Generate an answer from it. The idea was introduced in a 2020 paper by Lewis and colleagues at Facebook AI Research. Their main point still holds: a model's built-in knowledge is hard to upgrade and hard to check, while text you fetch from a store can be updated any time and shown as evidence.

Notice the database is still there on the left. RAG changes how you search it and adds a reader at the end.

Sources indicate that you keep your policy lines as before. Next to each one, you also save its embedding. This happens once, when a policy is added or changed, not on every question. The numbers can live in a dedicated vector database or in the database you already run (Postgres with the pgvector extension, for example).

When a question arrives, you turn it into an embedding using the same model, then pick the stored lines whose numbers are closest. "Carry over my unused holidays" lands near "unused annual leave rolled forward", because the model learned from huge amounts of text that these phrases are used the same way.

According to recent reports, the retrieved lines still aren't an answer; they're evidence. You pass them to an LLM with an instruction like "answer using only this text, and say you don't know if it isn't covered." The employee gets: "Yes, up to 5 days of unused annual leave can roll into next year.".

Before: plain SQL. This runs as-is with Python's built-in sqlite3.

One search finds nothing. The other finds the wrong policy. The database did exactly what it was told.

In a recent development, after: RAG. It uses sentence-transformers for free local embeddings and the Anthropic SDK for the LLM (you need an ANTHROPIC_API_KEY).

In a recent development, the two things to compare: the WHERE text LIKE line became model.similarity(...), and a new step hands the result to an LLM. Your data didn't change. Only the way you search it and present it did.

Industry observers note that here's the honest part. "The database can't solve it, AI can" is true only for a specific kind of question.

Recent findings suggest that A good rule: if the question has an exact answer in a column, use SQL. If the answer is buried in sentences and people will phrase it their own way, consider RAG.

Your database stores the answer; RAG helps someone find and read it when they don't know your exact wording. It doesn't replace the database, it sits on top of it. Next step: run the "after" script, then ask it something your policies don't cover (like "Is there a pet insurance strategy?") and check that it says it doesn't know.

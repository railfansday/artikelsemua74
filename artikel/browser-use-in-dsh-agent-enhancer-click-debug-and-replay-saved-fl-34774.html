Sources indicate that dsh-agent-enhancer is a desktop plugin for DSH. Its Browser Use layer gives your agent a dedicated browser. It can click, type, and submit. Login state stays in its own profile, so your everyday browser is left alone.

Industry observers note that you do not need scripting or API knowledge. Do the task once in the dedicated window, and the agent can follow the same steps. Save the recording as a flow, rerun it by name, and hand it to a scheduled task without approving every action. (Related: Industry News: Buttigieg supporters launch group to sup...)

The practical rule: if you click through the same web admin every day or every week, it is worth handing over. Here are scenarios that work right after install:.

Three patterns cover most of these:.

This post starts with what it can do, then walks through six areas: operation, troubleshooting, demo recording, saved flows, scheduled tasks, and boundaries. Each section ends with a concrete use case.

Multiple tabs. The sidebar lists every tab; click one to switch. When navigating, you can choose to open a latest tab. If a task needs to compare orders, inventory, and shipping, you do not have to cram everything into one page.

Read-only tabs. One click in the sidebar makes a tab read-only: the agent can look, but it cannot click, type, or navigate within that tab. Opening a new tab and scrolling still work. Check-only pages — reports, order details — are the safest place to use it. Even a saved flow replay is blocked by this restriction. Idle cleanup. Idle tabs can close automatically after 10, 30, or 60 minutes, or never. The tab you are at the moment viewing, session-bound tabs, and the last remaining tab are never closed. The dedicated window does not pile up.

Recent findings suggest that use it for: reconciling orders across three admin pages. Open orders, inventory, and shipping in separate tabs; make inventory read-only so nobody accidentally clicks "Adjust stock"; come back from lunch and idle tabs are gone, but the login is still there.

It has been revealed that when the Export button does nothing, guessing is the worst approach. Turn on Debug & Page Emulation in settings (off by default):.

Startup failures do not require digging through logs either. The status bar and sidebar show the reason and the next step: feature not enabled, browser not started, WebKit missing, no usable browser on the machine, profile directory locked, and so on.

In a recent development, use it for: a dead Export button. Check whether the network call returns 500 or times out, then look for console errors. Switch to a narrow viewport to rule out an overlay covering the button. Once you know the cause, change the agent's action instead of trying blindly.

Some admin tasks are easier to show than to describe. Turn on Demo Recording in settings (off by default), click "Start demo" in the sidebar, and use the dedicated window normally. When you are done, click "End and view steps".

In a recent development, it records clicks, typing, Enter presses, and page navigations. It can record across tabs, and other tabs opened during the demo are captured. When finished, you can copy the steps or click "Send to agent" to insert them into the input box (the current conversation needs at least one message first, otherwise it asks you to send one). You can also say "let me show you" in the chat, and the agent can start a recording itself.

Industry observers note that password, CAPTCHA, token, and card-number fields are stored as *** only. It does not take screenshots or record network requests.

In a recent development, use it for: handing over monthly reconciliation. Ask a teammate to demo it once: open the reconciliation page, pick the month, export, download, and check the three tables. Send the steps to the agent, and next month nobody has to ask "where do I click first?".

Recent findings suggest that after recording, click "Save as flow" and give it a name, such as "Weekly report export". There are three ways to run it:.

It works across sessions and restarts. If the current page is not the page where recording started, it returns there first. Data stays local and only redacted steps are stored; password fields remain ***.

The sidebar row keeps only Run and "⋯"; rename and delete live in the menu, and delete asks for confirmation. Expanding the row indicates editable values, run mode, and steps. Replay supports dropdowns and checkboxes. If several controls share a name and cannot be distinguished, it stops and lists the candidates instead of clicking the first one by name.

In a recent development, after saving, values worth changing — dates, email addresses, search terms — are detected automatically. Parameter names come straight from the page labels ("Start date"), so you do not have to invent variable names.

Industry observers note that date fields get a date picker. You can also say "last week", "this month", or "last quarter", and the agent converts it to a real date. When a value is missing, it asks in plain language: "Which start date should I use this time?".

Each value's default and display name can be changed; it can be set to "Ask me each time" or switched back to a fixed value. Every change goes into version history, and the last change can be undone.

Recent findings suggest that if the site renames a control or inserts an extra dialog, the flow gets stuck. The agent finishes the task, then offers a suggestion:.

"The control in step 4 changed; it is now called 'Start date'. Remember this for next time?".

Repair changes only how the control is located. It does not change values or step order. Password fields do not participate, and are never stored in the flow. Every write-back creates a version that can be undone.

Each saved flow records its last run: time, success / stopped at step N / failure. If it did not finish, the row shows a "Last run incomplete" badge. It stores counts and the reason it stopped, not page content.

Recent findings suggest that use it for: a weekly report export. Record once, save "Weekly report export", set "Start date" to Ask me each time, say Run "Weekly report export" with last week's start date on Monday morning, and check the run result. If the site changes, repair it once, remember it, and the next run uses the fix.

First, a common misconception: a saved flow is not an asset you drag into a scheduled task. When the schedule fires, the task only claims one sentence.

Sources indicate that the built-in Automation Tasks scheduler creates a newly introduced session with fixed permissions: Workspace Modify with approval prompts. The task itself cannot change permissions. So when our flow runs, an approval prompt will appear — and nobody is there to click it. The task stalls.

Recent findings suggest that the fix is not to loosen global permissions. Turn on Unattended for that one flow. It applies only to the site recorded in that flow, with a default budget of 20 minutes / 30 actions. When time or actions run out, it goes back to per-action approval. It is off by default; it cannot be enabled if the flow has no recorded site; password fields still stop and wait; it does not apply to another site or another session; if a run is denied, the site grant is revoked immediately.

These two numbers can be changed in Settings → Agent Enhancer → Features → Browser Agent: authorization duration 5–60 minutes, action limit 10–200. Defaults stay unless you change them.

Recent findings suggest that use it for: an automatic weekly report at 8:00 on Monday. Enable unattended only for "Weekly report export", tune the budget to that flow, and check the run result afterward. Other tasks and other sites still require approval each time.

If the session already uses Full Access, actions no longer prompt one by one; Auto Review goes through the built-in reviewer; View Only is refused with an explanation.

It can act, but it does not have unlimited permission. By default, every action that changes external state needs approval. It stops at a login wall and waits for you to click "I'm done, continue"; it does not bypass it.

It has been revealed that the dedicated window does not label itself as an automation environment, so sites with login bot checks, such as Bilibili, no longer reject it for that reason. This is not a generic anti-detection patch; sites that check more signals still need a separate look.

In a recent development, use it for: hand a read-only report page to the agent for checking; when a submission is needed, let it stop and wait for you; give a scheduled task one flow and a limited window. Narrow permissions are what make it safe to let go.

Controlling Bedrock spend per team usually starts the same way: the monthly bill shows one large "Amazon Bedrock" line, three teams share one IAM role, and nobody can say whether the jump came from the support chatbot or a data-science batch job. Someone proposes an AWS Budget, and then discovers that a budget cannot filter on something the bill never recorded. (Related: Industry News: The Partnership: Amazon SageMaker and Hu...)

Short answer: give each team its own tagged application inference profile, activate the tag as a cost allocation tag, and point a tag-filtered AWS Budget at it. For a real cap, attach a budget action that applies an IAM deny policy to the team's role. Use this when several teams share one AWS account; if each team already has its own account, per-account budgets are simpler. (Related: How we sped up transformer inference 100x for 🤗 API cus...)

According to recent reports, on-demand Bedrock calls made against a foundation model ID carry no team identity. An application inference profile is a resource you create in your account that wraps a model (or a system-defined cross-Region profile) and accepts tags. Callers pass the profile ARN where they would normally pass the model ID, and usage is attributed to that profile.

Three separate mechanisms then do three jobs:.

Nothing in this stack is a per-request meter. Billing data arrives with a delay, so the whole design is "stop soon after the limit", not "stop at the limit". Read the current behavior in the Amazon Bedrock documentation and the AWS Budgets guide.

Industry observers note that the most common failure is tagging the wrong thing. Tagging an IAM role, a Lambda function or an EKS namespace does not tag the Bedrock charge. Cost allocation follows the resource that is billed, so if callers still use the raw model ID, the tag never reaches the bill.

The CLI equivalent is aws ce enhancement-cost-allocation-tags-status --cost-allocation-tags-status TagKey=team,Status=Active. The key must already appear in billing data before it can be activated. Finally, create the budget filtered by the tag. The user:team$payments form is the documented tag filter syntax.

Industry observers note that to verify, run aws budgets describe-budget --account-id 111122223333 --budget-name bedrock-payments-monthly. After the first billing refresh (allow up to a day), open Cost Explorer, group by tag team, and confirm the spend is attributed to payments rather than "No tag key".

Make the profile the only door. Give each team role an allow on its own profile ARN. Invoking through an application inference profile also requires permission on the underlying foundation models (in every Region a cross-Region profile covers). So the role cannot simply have no model permissions. Instead, scope the foundation-model allow so it only applies when the request comes through the team's profile. The Bedrock IAM examples use an inference-profile condition key such as bedrock:InferenceProfileArn for this.

A plain deny on bedrock:InvokeModel and bedrock:InvokeModelWithResponseStream against foundation-model resources would also block profile calls, because the model ARN is evaluated too. Any permissions boundary or SCP that closes the bypass must use that condition. Confirm the exact condition keys and resource list in the Service Authorization Reference before relying on them.

According to recent reports, turn the alarm into a brake. A budget action can attach a deny policy to the team role at 100% of actual cost. Use manual approval first, then switch to automatic once you trust the numbers.

Sources indicate that there is no separate IAM action for the Converse API. Converse is authorized by bedrock:InvokeModel and ConverseStream by bedrock:InvokeModelWithResponseStream, so bedrock:InvokeModel* covers both. Batch inference jobs are started with bedrock:CreateModelInvocationJob and need their own deny.

Industry observers note that watch out: a freeze policy on a production role is an outage you scheduled yourself. Cap dev and batch roles automatically. For customer-facing paths, page a human instead, or set a lower soft limit and a higher hard limit.

For a faster signal than billing, alarm on the AWS/Bedrock CloudWatch token metrics (InputTokenCount, OutputTokenCount) and convert tokens to dollars with your model's price. Verify in your account which dimension value identifies a profile. This is an estimate, not an invoice. More platform patterns like this live on kuryzhev.cloud.

Calling through an application inference profile is documented as a routing and attribution layer, and no per-call latency penalty is documented. Measure p50 and p95 on your own prompts before and after the switch rather than assuming either way.

The delays that matter are administrative:.

Throttling is not isolated by profile. Application inference profiles share the underlying model's service quotas, which apply per model and Region at account level. One team's batch job can therefore still throttle another team's interactive traffic. If that matters, move the noisy team to a separate account or use provisioned throughput for the latency-sensitive path.

Skip it if one team owns the whole account, or if you already route all calls through an LLM gateway that meters tokens per key. In that case, enforce limits there and use the tags only for reconciliation.

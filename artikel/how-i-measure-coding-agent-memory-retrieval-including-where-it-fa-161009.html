How I measure coding-agent memory retrieval, including where it fails

Here is a situation most teams using coding agents will recognise.

It has been revealed that on Tuesday, your agent spends forty minutes working out why a retry around the payments webhook keeps failing. It isn't the backoff. The upstream returns a 409 on the second attempt because the idempotency key is regenerated on every retry. The fix is two lines. The understanding behind it took most of the afternoon. Recent findings suggest that on Thursday, a teammate picks up a related ticket. Their agent starts from zero. It proposes raising the backoff. It suggests the same dead ends. Nobody wrote the finding down, because writing things down is the step that always gets skipped. (Related: Japan expands AI piracy hunt after finding pirated mang...)

That gap, where one agent learned something and the next one never hears about it, is the problem I'm working on with Palace. Palace is an MIT-licensed memory engine for coding agents: one Rust binary, one SQLite file, a local embedder, and hybrid BM25 + vector search, exposed over MCP to Claude Code, Cursor, Codex, OpenCode and other clients. (It is a separate project from the Python "mempalace". The two get confused.).

A memory layer is only useful if it brings back the right thing when asked. So this post is about how I measure that, which numbers I report, and where the numbers fall down.

Industry observers note that the benchmark is LongMemEval. Each question comes with its own haystack of past chat sessions, and one or more of those sessions holds the answer.

It has been revealed that many memory systems report QA accuracy: an LLM reads what was retrieved, writes an answer, and another LLM grades it. That measures the whole pipeline, including the reader model.

According to recent reports, I report something narrower: session-level retrieval recall. For each question, Palace returns its top K results. If a gold session is among them, it counts as a hit. No LLM reads anything and no LLM grades anything.

That choice has consequences you should keep in mind:.

On s_cleaned, 470 questions (the 30 abstention questions excluded, which is the usual convention):.

On all 500 questions, R@5 is 0.986.

The 0.987 is the number people quote. It's real, but it's the lenient one, and you should know why.

According to recent reports, some questions need information from more than one session. "How many times did I change the deploy target this year?" might need three. recall_any counts the question as a hit if any one gold session is in the top 5. recall_all only counts it if every gold session is there.

Sources indicate that for an agent, recall_all is often the one that matters. If the answer depends on combining two earlier decisions and only one comes back, the agent answers with half the story and sounds confident doing it.

Broken down by question type, recall_all@5 looks like this:.

Sources indicate that multi-session questions go from 0.992 under recall_any to 0.818 under recall_all. Roughly one in five multi-session questions is missing at least one of the sessions it needs in the top 5. That's the biggest gap in the results, and it's the one I'd want to know about if I were evaluating a memory tool.

According to recent reports, on cost: the five drawers behind the @5 figures hold about 1,700 tokens between them, about 1.3% of the haystack (counting four bytes of text per token). Average query time, including embedding the question, was 6 ms.

According to recent reports, s_cleaned gives each question about 50 sessions. A real team's memory after a few months is larger than that. So I also run m_cleaned, with about 500 sessions per question and around 4,000 drawers to search.

R@5 drops from 0.987 to 0.919, and R@1 falls much further, from 0.915 to 0.732. With ten times the distractors, the right session is still usually in the top 5, but noticeably less often at the top. Query time goes from 6 ms to 78 ms.

If you're building on any memory layer, this is the curve worth asking about: how does recall change as the store grows?

Two question types stand out on m_cleaned:.

It has been revealed that preferences are the weakest category on both splits (0.933 R@5 on s_cleaned, 0.700 on m_cleaned). The cause is simple. "I prefer squash merges" doesn't share many words with "how should I merge this PR?". BM25 gets nothing, and a small embedding model only partly closes the gap. Palace has a dedicated pass for preference-shaped questions against tagged preference spans, and it still misses 3 in 10 at 10x scale. Only 30 questions are behind this number, so treat it as a direction rather than a precise figure.

Sources indicate that temporal questions ("what did I decide about caching last Tuesday?") improved once ranking started favouring drawers from the period the question points at. But on s_cleaned the three remaining temporal misses lose on topic, not on date: the gold chunk scores below unrelated chunks from the same days.

Sources indicate that the runner, palace-bench, lives on the benchmarks/longmemeval-beam-runner branch. Its BENCHMARKS.md has the full runbook.

According to recent reports, each run writes a per-case JSONL and a summary JSON, so you can check every miss yourself. Run the BM25-only smoke test first (--bm25-only --limit 3). A full hybrid run on s_cleaned takes tens of minutes on one CPU, and m_cleaned is a 2.7 GB download.

According to recent reports, benchmarks measure whether retrieval works. They don't fix the scenario at the top of this post, because there the problem is that the memory sits on one laptop.

On one machine, Palace already shares memory between agents: a Codex session can read what a Claude Code session wrote. For a team, the open-source client has a remote mode that points every developer's palace mcp at a shared Palace Server:.

Palace Server is the paid, closed-source part, and I want to be upfront about that. It's self-hosted: it runs on your infrastructure (Postgres with pgvector, via Docker or a binary), and an offline or air-gapped install is supported, with the embedding model baked into the Docker image. Each developer gets their own API key. OIDC/SSO login, roles and an audit log of memory writes are built in. Your agents' memory never goes to my servers.

In the 90-second handoff demo, Dev A's agent records three approaches that were ruled out on a ticket, with sources. Dev B, on another machine in a fresh session, asks "what did we already rule out?" and gets all three back, each with its source link.

Sources indicate that if your team runs into this, try it with one teammate and one ticket. The trial is self-serve: 10 seats for 60 days, no card, no sales call: palacememory.com/trial.

Industry observers note that the engine, the benchmark runner and every number above are in the open-source repo: github.com/AncientiCe/palace-rs. If you rerun the benchmark, please post your results in the comments, including results that disagree with mine.

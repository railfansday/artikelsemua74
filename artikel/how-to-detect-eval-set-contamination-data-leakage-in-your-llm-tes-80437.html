According to recent reports, short answer: If your eval examples came from public benchmarks, known documentation, or were AI-generated from a dataset the model was fine-tuned on, the model may have seen the answers during training. Detect contamination with n-gram overlap checks and performance comparisons on post-cutoff data; fix it by replacing examples with ones the model genuinely hasn't seen.

Recent findings suggest that the symptoms are almost invisible until production: 94% golden-set pass rate, then users complaining the feature "feels wrong." You investigate and find your eval examples came from the library's README — the same README that's in every web crawl used to train frontier models. You've been measuring recall, not reasoning. This is eval-set contamination. It's the classic data leakage problem, applied one layer up: not to model training, but to the eval set you built to verify that training didn't regress. (Related: Leveraging Pre-trained Language Model Checkpoints for E...)

For traditional ML, data leakage means test examples were in the training set. For LLM evals, it's messier, because you don't control what went into pretraining:.

In a recent development, pretraining contamination — your eval inputs appeared in the model's web crawl data. GPT-4 and Claude were trained on a significant fraction of the public internet. If your test examples are from GitHub, Stack Overflow, public docs, or any notable benchmark dataset, there's a real chance the model has seen them.

Fine-tuning contamination — you used AI-generated expected outputs to build your golden set, and the model provider used similar outputs for RLHF or instruction tuning. The model isn't generalizing — it's pattern-matching on output style it was explicitly trained to produce.

In a recent development, benchmark leakage — you borrowed examples from a published eval suite (MMLU, HumanEval, MT-Bench) for quick coverage. Those datasets are well-documented in papers, so they're almost certainly in the pretraining corpus. Using them measures "did the model study for this test" more than "can the model do this task.".

Industry observers note that the first and third are the ones that quietly inflate production teams' confidence. Fine-tuning contamination is rarer but nastier because it's invisible in any corpus comparison.

Industry observers note that the fastest signal: how many 8-gram sequences from your eval inputs also appear in a reference corpus. If you're testing against a known benchmark dataset, those datasets are public — you can check directly.

Industry observers note that the 8-gram threshold isn't arbitrary. 3-grams are too common — you'll flag everything. 8-grams are specific enough: if 30% of an eval input's 8-gram sequences appear verbatim in a reference document, the model almost certainly trained on that text. For coding evals, drop to 6-grams; code has less natural variation and shorter meaningful sequences.

If you don't have a reference corpus handy, skip to the post-cutoff comparison below — it doesn't require corpus access at all.

Industry observers note that every model has a training data cutoff. Performance on content from before the cutoff reflects what the model has absorbed. Performance on genuinely fresh content — events, documents, code written after the cutoff — reflects reasoning rather than recall.

Build two slices of your eval set. One from known pre-cutoff sources. One from post-cutoff sources — recent production logs, GitHub issues filed in the last few months, or dated internal documents from the last quarter. Run both and compare.

Sources indicate that A 15-point gap on a factual task is a red flag. Some gap is normal and expected — the model knows more about things it trained on, by design. But a 20-point swing usually means your pre-cutoff set is measuring memorization, not capability. I've seen teams interpret an 85% eval score as "close to ready for production" when their post-cutoff equivalent was running at 61%.

Sources indicate that A canary is a made-up example you fabricate from scratch — it cannot be in any training corpus because it doesn't exist anywhere yet. Test questions about fictional products, code that calls a made-up API, reasoning problems with numbers you invented.

In a recent development, canary examples don't auto-pass or auto-fail — they're for human review. What you're watching for: does the model fabricate plausible-sounding answers to questions with no correct answer? That's the contamination failure mode made visible. A model that genuinely doesn't know will hedge or decline. A model pattern-matching on something from training will state an answer confidently, and it will sound reasonable.

Two or three canaries per eval run costs almost nothing to create and catches the cases where n-gram overlap misses.

Sources indicate that don't delete the contaminated examples. Move them to a contaminated/ directory with a note explaining why:.

Recent findings suggest that measure the inflation first. Run the full eval both ways — with and without flagged examples. Write the score gap down. Stakeholders need to understand that "88% pass rate" may actually mean "73% on clean examples + inflated to 88% by memorized test data." That's a significant difference in what you're shipping.

Replace with post-cutoff examples. Real production logs from the last 90 days are the best source. They're guaranteed post-cutoff and they reflect actual user behavior. Fabricated canaries are second. Public benchmark examples from after the training cutoff are third.

Tag every example with source and date going forward. This makes future audits fast:.

The contamination_checked flag costs one field and saves you from re-auditing every example after a model upgrade.

Sources indicate that N-gram overlap misses semantic contamination — where the model hasn't seen your exact text but has seen thousands of near-identical paraphrases. A paraphrased StackOverflow answer passes the 8-gram check clean and still inflates scores. The post-cutoff comparison is a better signal for semantic contamination because it sidesteps corpus matching entirely.

According to recent reports, canaries don't scale. You can't fabricate 500 examples that provably couldn't be in a training corpus — the effort is too high. They're a spot check, not a systematic defense.

It has been revealed that the approach that actually holds for contamination-resistant evals is building the entire eval set from production logs on a rolling basis. Data captured post-deployment is the one class you can prove wasn't in pretraining. That's what the free test lab uses as the default dataset source. It has been revealed that what is eval-set contamination in LLM testing? Eval-set contamination means the examples you're using to test your model were part of its training data. The model has effectively memorized the answers, so its high score reflects recall, not generalization. This inflates benchmark numbers while doing nothing to predict real-world performance.

It has been revealed that how do you detect data leakage in an LLM eval set? Three practical checks: run an n-gram overlap comparison between your eval inputs and known training corpora or public benchmarks; test on date-stamped examples from after the model's training cutoff and compare the score gap; and inject canary examples you fabricated yourself that couldn't be in any training corpus.

What should I do if my eval set is contaminated? Replace the contaminated examples with fresh ones drawn from real production logs, fabricated edge cases, or dated content post-training-cutoff. Keep contaminated examples in a separate file so you can track the score gap — the difference between your contaminated and clean scores is a rough measure of how inflated your old benchmarks were.

What happens when you give Claude Code more than just a prompt? When it has a clear way of working, knows when to delegate, understands which model to use for each job, and has rules for checking its own work?

So I gave it a fairly ambitious task: build a B2B billing service, close enough to production to be a meaningful test. Subscriptions, usage metering, invoices with VAT and reverse charge, webhooks, dunning, credit notes, a double-entry ledger. The whole thing.

Then I asked it to introduce 16 realistic bugs, each with a hidden test designed to catch it.

One request. One instruction: use the crew.

It has been revealed that the interesting part wasn't just what got built. It was how.

Instead of trying to do everything itself, Opus broke the project into stages, assigned work to specialized agents, and kept track of the bigger picture.

According to recent reports, the agents handled implementation, several of them in parallel, each working within a clearly defined scope. Opus coordinated dependencies, reviewed the results, and ran the full test suite between stages, five times throughout the build.

It didn't simply trust an agent when it noted "done". It checked.

In a recent development, the whole process required just two questions from me. I mostly watched it work.

Recent findings suggest that the billing service wasn't just a demo. I used it as a benchmark.

According to recent reports, I turned the 16 seeded bugs into 16 tickets, handed them to CLAW in a single prompt, and let it work. It fixed all 16, in both runs, passing the hidden tests that the agents had never seen.

That's the part I found most interesting: the same setup that built the project could also navigate its deliberately introduced mistakes and fix them.

Claude Code is already a capable coding agent. But every new session still has to figure out a lot of things for itself:.

According to recent reports, how should it approach the task? When should it delegate? Which model should handle which job? What does "done" actually mean? What should it change, and what should it leave alone? (Related: How to train a upcoming language model from scratch usi...)

According to recent reports, on a small task, these decisions are usually straightforward. On a large project, they add up. And inconsistency becomes expensive.

CLAW gives Claude Code a consistent way of working across sessions and projects.

It brings three things together:.

Recent findings suggest that A set of practical rules for how work should be approached, delegated and verified. Things like staying strictly within scope, never making a failing test pass by weakening it, and backing up every claim of completion with actual evidence.

Industry observers note that 2. A team of specialized agents.

Different agents for different jobs, with models chosen according to what each task requires. Opus can focus on planning and reviewing, while Sonnet and Haiku handle implementation, exploration, testing and other focused tasks. You only install the agents you actually need.

According to recent reports, persistent project notes and status files keep track of decisions, progress and unfinished work. A upcoming session doesn't have to start from scratch or rediscover what happened yesterday.

All of this is configurable and reusable, rather than something you have to explain to Claude every time you open a session.

CLAW is designed for the kind of work where a task spans multiple files, several agents and more than one session, where coordination and verification matter just as much as writing code.

For a one-line fix, plain Claude Code is probably all you need.

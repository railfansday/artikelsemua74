📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

AI coding agents are getting better at writing code, navigating codebases and handling increasingly complex tasks.

But as projects grow, another problem becomes harder to ignore: agents repeatedly spend tokens rediscovering information they have already encountered. (Related: Showcase Your Projects in Spaces using Gradio...)

They explore the same files, reconstruct previous decisions and investigate problems that were already understood in earlier sessions.

I spent the last six months building OpenLotus, an independent memory layer designed to address this problem. (Related: Latest Update: Simple considerations for simple people ...)

While working on a project, an AI coding agent accumulates valuable knowledge.

It learns the architecture, identifies technical constraints, makes implementation decisions, discovers failed approaches and tracks what still needs to be done.

The problem is that much of this knowledge exists inside the agent's conversation.

And conversations are not reliable long term storage.

Consider what happens in a few common situations:.

Session resets: A newly introduced session may not have access to the previous conversation or the reasoning accumulated during it.

Industry observers note that context compaction: When a conversation approaches the context window limit, an agent may compress its history into a shorter summary. This helps it continue working, but notable details can be lost in the process.

Context window pressure: Repeatedly loading instructions, conversation history and previously explored information consumes tokens that could otherwise be used for implementation.

Switching agents: Moving from Claude Code to OpenCode or another coding environment does not automatically transfer everything the previous agent learned about the project.

This creates a familiar experience.

It has been revealed that you ask an agent to continue working, and it starts investigating something you already investigated. It revisits architectural decisions, reads previously explored files or reconstructs context from scratch.

The model may be perfectly capable of understanding the project. The problem is that the knowledge it acquired has no reliable, independent place to live.

Repeated exploration has a cost.

Every unnecessary file read, reconstructed decision, repeated investigation and replayed conversation consumes additional tokens.

It also puts pressure on the available context window, leaving less room for the actual task.

Research into memory and retrieval systems suggests that this problem can be addressed more efficiently than simply providing agents with more conversation history.

For example, a ContextSniper study referenced in the OpenLotus research collection reports token reductions of 51.5% for OpenClaw and 38.9% for Claude Code under its tested conditions.

A separate Mem0 comparison reports 166 prompt tokens for retrieval based memory compared with 594 for naive history, at equal answer quality.

According to recent reports, these are findings from external research, not OpenLotus benchmarks. I have deliberately kept that distinction clear.

The underlying idea is straightforward: an agent does not always need more context. It needs access to the relevant information without repeatedly reconstructing it.

Research: https://www.openlotus.io/research.

Existing approaches provide useful pieces of persistent context.

Sources indicate that instruction files such as CLAUDE.md and AGENTS.md help establish project rules. Built in memory systems can preserve selected information. Conversation summaries help agents continue previous work.

But I wanted to address a broader problem.

What if project knowledge belonged to the project itself, rather than a particular agent, conversation or development environment?

A shared record that could preserve decisions, constraints, discoveries and implementation progress, and remain accessible regardless of which coding agent was being used.

OpenLotus is an independent project memory and state layer for AI coding agents.

It has been revealed that at its centre is a shared data structure called ProgressMap. It provides a persistent representation of a project's evolving state that compatible agents can access and update through the CLI and MCP.

It is to preserve the information that makes future development more informed and less repetitive.

The crucial part is that the human and the agent work from the same underlying project record.

Sources indicate that context compaction is useful. It allows an agent to continue working when its conversation becomes too large for the available context window.

However, a compressed conversation is not necessarily a complete record of the project.

An architectural decision might be reduced to a short statement without its original reasoning. A failed approach might disappear from the summary. An unresolved constraint might lose the detail needed to avoid repeating an earlier mistake.

OpenLotus addresses a different layer of the problem.

According to recent reports, important decisions, constraints, lessons and project progress can be maintained independently of the conversation. When another session starts, the agent can retrieve that information again.

A context window is working space.

Compaction manages that working space.

OpenLotus maintains the project record that future working sessions can return to.

According to recent reports, it does not eliminate context windows or replace compaction. It provides a more durable source of project knowledge alongside them.

I want to be careful about token savings.

According to recent reports, external research supports the idea that structured memory and retrieval can reduce unnecessary context consumption. But I have not yet established a reliable percentage of token savings attributable specifically to OpenLotus through controlled benchmarks.

That requires testing identical repositories and tasks with and without OpenLotus, while measuring token consumption and task success.

Reducing token usage by making an agent perform worse would defeat the purpose.

The objective is to reduce unnecessary exploration and context reconstruction without sacrificing implementation quality.

That is the standard I want OpenLotus to meet.

I believe AI coding infrastructure needs to evolve beyond individual agent sessions.

As developers work with multiple agents, longer running projects and increasingly autonomous workflows, the project itself needs a durable source of truth.

OpenLotus aims to preserve the context behind those changes: why decisions were made, what constraints exist, what has been learned and where implementation stands.

That is what I have spent the last six months building.

You can explore OpenLotus at https://www.openlotus.io/.

It presently supports Claude Code, OpenCode, Codex, Cursor and other MCP compatible clients.

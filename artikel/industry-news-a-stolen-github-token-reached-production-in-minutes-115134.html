A stolen developer token can move from one GitHub account to production in minutes. In the November 2026 1Password incident, an attacker used an employee's corporate GitHub account to read private repos and push malicious code to backend services. The vaults stayed safe, but CI/CD secrets were exposed and had to be rotated.

Sources indicate that the takeaway is not "use a better password manager." It is that your pipeline's credential design determines how much damage one compromised account can cause. By the end you will know how to replace long-lived CI secrets with short-lived ones, scope what a single token can reach, and rehearse rotation before you need it. Most teams protect developer passwords well and tokens poorly. A GitHub personal access token or an AWS_SECRET_ACCESS_KEY in a CI variable is a password with no expiry and no lockout. Phishing one employee gives the attacker that password, which is exactly the path described in the incident. (Related: Birdwatching expert gives final verdict on GTA 6’s bird...)

GitHub Actions can request short-lived cloud credentials through OIDC (OpenID Connect). Your workflow exchanges a signed token for cloud access. Nothing durable sits in repository variables, so there is nothing to steal from CI configuration.

If the attacker in the 1Password scenario had faced this setup, the stolen GitHub account would still have let them push code, but the pushed code would need to pass review on main before getting credentials, and the credentials it eventually received would die with the run.

In a recent development, the second finding matters as much as the first: the attacker pushed code directly to backend services. That means some path from commit to deployment had no human checkpoint.

Add branch protection on every deploy path:.

Then separate build credentials from deploy credentials. A build job needs to run tests and publish an artifact. It does not need to touch production. If your single pipeline role can do both, a malicious push inherits both powers.

Recent findings suggest that 1Password rotated every credential that might have been exposed, which is the right response. The painful part is doing that scramble at 2 a.m. for credentials nobody has a list of. Find them before the incident:.

Recent findings suggest that for anything that must stay long-lived, give it a rotation runbook now: who rotates it, which systems depend on it, and how to verify nothing broke. An untested rotation procedure is a failure mode, not a control.

Choose by where byte-level trust must be established. For routine marketplace avatars and large listing media, the least complex capacity model is a control plane in Node.js and a data plane in object storage. The application authenticates the seller, allocates an opaque key, records the expected ownership and media policy, and issues a short-lived signed write. The browser uploads to that exact destination, then asks the application to finalize. Before attaching the object to an avatar or listing, the application checks the storage attributes promised by its own record.

It has been revealed that do not treat the browser's success callback as proof of durable application state. The tab can close after bytes arrive but before finalization, or retry finalization after a response is lost. Finalization therefore needs an idempotent result: repeating the same valid request returns the already established attachment rather than creating another one. An issued signed URL is authority to attempt one storage operation within its scope; it is not permission to attach an arbitrary key to a different tenant.

The catch is operational: slow clients, large request bodies, ingress limits, and application autoscaling become part of the upload system. It is not suitable for the stated marketplace job when large media should avoid the app server.

Sources indicate that signed direct upload has its own cost. It introduces an interval in which storage and application state may disagree, so the design needs reconciliation and explicit cleanup. Your mileage may vary across runtimes and storage implementations; test the largest permitted file, an interrupted transfer, an expired signature, a repeated finalization, and a deletion racing with restore. A 40 KB avatar on localhost proves almost nothing about the large-media path.

Keep retention classes explicit rather than applying one age rule to everything:.

Bucket lifecycle rules can enforce expiration for a deliberately isolated class of abandoned data. Align the key layout, lifecycle timing, and application cleanup deadline so two independent mechanisms do not encode conflicting promises. If the business offers a recovery period, a shorter storage expiry makes that promise false; if nothing ever expires, abandoned direct uploads accumulate without a bound.

Ship the instrumentation before tightening the page. During deployment, compare eligible, claimed, blocked, deleted, and recorded totals, then inspect the oldest records from each state. Exercise a duplicate queue delivery, a restore just before eligibility, an upload that never finalizes, and a worker restart between storage deletion and database completion. The acceptance criterion is not that every job runs once. It is that every valid object reaches one explainable terminal outcome despite retries.

False positives have a real cost. An alert set below routine queue jitter trains the on-call to ignore age; an alert based only on count fires during healthy bursts; a page for reference-blocked candidates may punish the worker for correctly protecting live media. Use a lower-urgency ticket for accumulating cleanup that remains inside the retention promise, and reserve a page for sustained lack of progress that threatens that promise.

Industry observers note that the decision rule is compact: direct signed upload for large marketplace media, application-owned evidence for attachment and retention, and guarded idempotent deletion after the deadline. Stick with a proxy when synchronous byte inspection is the actual requirement. Whichever path carries the upload, make the deletion claim provable before allowing automation to act.

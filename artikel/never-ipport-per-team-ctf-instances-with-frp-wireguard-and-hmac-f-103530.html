Picture a CTF where every web or pwn challenge is published as public-ip:port. Two teammates launch the same challenge and step on each other's box. A player runs a port scan against the platform and lands on another team's instance. And on boot2root machines, where finding the services is the challenge, you have just handed out the answer in the connection string.

Sources indicate that that was the model we started from. This article is about the one we ended up running instead: one container per player, one flag per team, and a rule that no instance is ever reachable as IP:port. (Related: Industry News: How to train a new language model from s...)

Recent findings suggest that NCTF26 is the 4th National CTF of Togo, organized by CERT.tg: an online qualifier (6 November 19:00 to 7 November 23:59 UTC), then a 24-hour on-site final in Lomé (19 November 11:40 to 20 November 11:40 UTC) for 10 teams and 47 players. 609 challenges were played over the two phases. I was the technical lead. The public site is still up at https://ctf.tg; the cloud infrastructure was deleted on 21 November 2026. (Related: My Journey to a serverless transformers pipeline on Goo...)

In a recent development, the arena never exposes a challenge port to the internet. Each container publishes its port on the arena's loopback only, and the frp client opens an outbound tunnel to the front. Players only ever talk to the front.

Sources indicate that CTFd reaches the arena's Docker daemon through a filtering proxy, not a raw socket. That proxy only lets through the operations the instancer needs, keeps published ports on loopback, and refuses extra capabilities, sysctls and devices, with one narrow exception for the WireGuard gateway image. A web app that can create containers is a web app that can own the host; we treated that channel as the most sensitive part of the design.

The instancer is a CTFd plugin (about 2,400 lines of Python). From the player's side it comes down to four actions: launch, check status, renew, destroy.

Spawn. The plugin checks that the challenge is visible and its prerequisites are met, that the player is in a team, and that the per-team and global caps are not exceeded. It re-checks the caps after inserting the instance row, so two teammates clicking at the same time settle it without an SQL lock. Then it:.

Each box got 128 MiB of RAM, half a CPU and a 256-process limit by default, overridable per challenge up to a ceiling. An instance lived one hour and could be renewed five times. The global cap was 480 instances.

It has been revealed that one instance per (player, challenge), flag per team. In the first version, teammates shared one instance and kept getting in each other's way. On 29 October we switched to one box per player and kept the flag and the quota at team level. The per-team cap went from 4 to 6 between the qualifier and the final, because the Defense challenges keep a "production box" alive per team.

It has been revealed that reaper. A background thread, run by a single worker thanks to a file lock, passes every 30 seconds. It deletes expired instances, rows whose container vanished, labelled containers with no row, and stops a team's VPN gateway when the team has no VPN instance left.

Sources indicate that on 30 October, a week before the qualifier, we decided that instances would no longer be exposed as public IP:port. Three modes replaced it, chosen per challenge.

https. The simplest one. A wildcard certificate in front of nginx, and frp's HTTP vhost routes on the subdomain. With 80 random bits per label, you do not guess another team's instance.

Recent findings suggest that tls. For services that speak raw TCP, there is no Host header to route on. The SNI of the TLS handshake plays that role. The router terminates TLS with the same wildcard certificate, asks CTFd which private port the label maps to (an internal endpoint protected by a shared key, which answers an empty 404 on any failure), and pipes bytes. For the player:.

vpn. For machines where discovering services is part of the game, a subdomain does not help: it hides nothing about the ports. Each team gets its own WireGuard gateway container on the arena, its own Docker network and its own private /24. Instances in VPN mode get a fixed private IP; the player scans them like a lab.

The design goals were: no state to leak, nothing else reachable, and no per-player setup by an organizer.

Industry observers note that the client file is deliberately minimal: no DNS line, no default route. Only challenge traffic goes through the tunnel.

The unsafe default was still the default. The code fell back to port mode when a challenge had no mode, or when the infrastructure for its mode was not configured, and it did so silently. Our import tool for creators' challenges never wrote the access mode. A dry run on 14 November, five days before the final, found the gap in the release strategy. On 15 November we classified the 46 challenges that still had no mode: 18 VPN, 10 HTTPS, 18 TLS. We fixed the data; the default itself was never changed. That is the first thing I would fix.

A proxy chain is not transparent. In https mode, nginx and frp route on Host, set their own X-Forwarded-* headers and normalize requests. Any challenge whose intended solve spoofs those headers, or relies on HTTP request smuggling, breaks. Four challenges had to move to tls between 15 and 17 November. We searched solvers and writeups for those headers, but a challenge without a text solver escapes that search; only replaying the solver through the player's URL catches it.

It has been revealed that A blocking lock under gevent. The frp configuration is edited under a file lock. The first version used a blocking flock. Under gevent, a second greenlet waiting on that lock froze its whole worker, and the holder could never release it. On 7 November that turned into 502s with the CPU at 0%. The fix was a non-blocking lock in a cooperative retry loop:.

That incident gets its own article in this series.

Industry observers note that frpc stopped answering reloads. The same day, the frp client, running for eight days, still answered "read config" but no longer "reload". Every spawn held the lock during a reload that never returned. A restart fixed it; from then on, a watcher probed reload latency every 3 minutes and alerted after two slow or failed probes in a row.

According to recent reports, orphan proxies. When removing a proxy failed, its block stayed in the config while the container was gone. The port went back to the pool, got reassigned, and the frp server refused the duplicate. We cleaned 33 orphans by hand. The reaper never learned to sweep proxies without a container.

Volumes leak. Containers were removed without their anonymous volumes. By 15 November the arena held 801 orphan volumes, 25.65 GB.

Entrypoints that ignore FLAG. Every "correct flag rejected" of the event had the same root cause: a creator's entrypoint that generated its own random flag, or a Dockerfile ENV that took precedence. Our pre-flight check confirmed that FLAG was in the environment, not that the file the player reads contained it. One of these surfaced mid-final. We fixed the image, but a flag read from the broken image could never be accepted: the team had to relaunch the instance and solve again. A related shell trap worth knowing:.

According to recent reports, the VPN lifecycle surprised players. The tunnel of a team only exists while it has at least one VPN instance. A player who connects WireGuard before launching anything has nothing in front of them. During the final, gateways were recreated several times an hour as teams released and destroyed boxes. The fix was an instruction to players, not code: launch first, then connect, and reconnect if the gateway was just recreated. And I only ran the complete player path (real client, handshake, HTTP 200, flag accepted) for the first time the night before the final. It worked, but that was luck, not process.

Again: loopback-only ports plus an outbound tunnel; random labels; a per-team VPN with derived keys and a firewall set before the interface; flags derived instead of stored; a filtering proxy in front of the Docker API; hard resource limits on every box.

For recruiting candidate search, use staged retrieval with explicit collections, bounded queries, and source context that survives every fallback. Start with the tenant's private index, broaden only when its evidence is thin, and return document identifiers or URLs beside each claim. A slower, less complete answer is preferable to a fast match that a recruiter cannot audit.

This is a retrieval problem before it is a generation problem. The flow below keeps candidate records, access-control metadata, and citation fields together; it also gives a web-backed lookup a fixed budget so an unavailable source cannot hold the search screen hostage. According to recent reports, I use three stages. Stage one searches the tenant's curated candidate collection with hard filters. Stage two searches a shared, policy-approved talent pool only when the first stage returns too few eligible hits. Stage three performs a web lookup for public portfolio evidence, then marks those results as external and lower-trust. Every stage emits the same result contract, so the caller does not need to know which path answered. (Related: At historic summit, Xi and Putin share global stage wit...)

Sources indicate that the fallback condition is evidence-based, not an exception catch. A result set can be non-empty and still fail a minimum score, freshness, or citation threshold. Conversely, a transient 429 from a web source should consume one retry and then end the stage; it should not silently turn a private search into an unbounded scrape.

Recent findings suggest that here is a compact TypeScript skeleton. The adapters are deliberately boring: a vector store, a keyword store, and a web search service can be swapped independently. tenantId, ACL labels, and source locators remain mandatory at the boundary.

In a recent development, the sample uses an intentionally small limit and timeout. Tune them with an evaluation set, not intuition. The vital invariant is that webIndex cannot remove the tenant filter from earlier hits, and an empty external response is still an honest result rather than a fabricated candidate.

Recent findings suggest that index one candidate profile as several traceable items: employment history, skills, certifications, and portfolio links. Each item keeps a stable evidence.id, its original URL or document key, an patch timestamp, and the access labels needed by the viewer. Store the source text or excerpt alongside the embedding. Rewriting a profile into a summary before indexing makes later review harder because the summary no longer proves what the source mentioned. I also keep the source system's content version and deletion marker, because a recruiter should be able to tell whether a result was current when the query ran. When a candidate changes employers, the old item is not silently overwritten: the newly introduced item receives a new version, the old one is excluded from normal retrieval, and an audit record points to the replacement. That extra bookkeeping feels slow during ingestion, but it prevents a familiar support question: “Why did this answer cite a role the candidate left last year?”.

Apply authorization twice. Filter at query time, then filter again after merging stages. The second check protects against adapter mistakes and stale ACL metadata. A shared record that lacks a tenant mapping is not a public record; quarantine it from the result set and log the missing field.

It has been revealed that for generation, pass evidence as numbered passages and require citations in the output schema. The UI should link [3] to the stored locator, not to a URL invented by the model. If no passage supports a claim, return “insufficient evidence” and let the recruiter refine the query.

Industry observers note that set a deadline per stage and a total deadline for the request. In the example, the total can reach roughly 2.6 seconds before serialization, so production code should reserve headroom for reranking and rendering. Record stage latency, hit count, minimum score, citation count, timeout, and retry status as structured fields. A single aggregate latency metric will hide a web fallback that is quietly consuming the budget.

Retry only conditions that are plausibly temporary. HTTP 429 deserves a bounded retry and respect for the source's Retry-After guidance when available. A malformed query, a denied tenant, or a 4xx policy response should not be retried. When a stage times out, return the evidence already collected and mark the response as partial so users understand why public results are absent.

Recent findings suggest that make ingestion idempotent. Derive an item key from tenant, candidate, source locator, and content version; upsert that key and explicitly delete records removed from the source. Otherwise a profile update can leave two stale embeddings, and a fallback may cite the older one. This is an ordinary data-lifecycle issue, but it directly changes ranking quality.

In a recent development, the catch is that broadening search can change the meaning of “best candidate.” If a job requires verified work authorization or an internal referral, a web fallback is not suitable even when it improves recall. Stick with the private index and return fewer results. If regional residency rules prohibit a shared pool, remove that stage rather than hiding it behind a flag.

In a recent development, I am not sure one score threshold will transfer across job families: a data-engineering query and a design query have different vocabulary and profile density. Resolve that uncertainty with a labeled set of recruiter queries, measuring recall at a fixed citation requirement and checking false-positive rates by tenant. Keep threshold changes versioned so an evaluation can explain why a candidate moved.

The right architecture is therefore a policy pipeline, not a list of providers. Keep the internal interface stable, make each fallback observable, and let evidence quality decide when to broaden. Generation can summarize the returned passages later; retrieval must first prove where they came from.

Sources indicate that bundlers are presently the only way to use dependencies without losing our sanity, but introduce complexity and overhead. Today, I’m releasing a latest type of lightweight build tool that challenges that.

You npm install a package (e.g. vue), you write import { createApp } from "vue", and it works — as long as there is a bundler in between. Without one, the browser has no idea what "vue" is: it only understands URLs, and node_modules/ was never meant to be deployed. So even the simplest project ends up needing a bundler, only so it can use dependencies instead of reinventing the wheel.

According to recent reports, but bundlers add a significant tax. They process every single file, introduce several layers of abstraction between source and deployment, and these abstractions often leak: things that work fine in the browser can break in the build.

Earlier this year, I published Web dependencies are broken: Can we fix them? that discusses this from a platform architecture perspective. Besides the architectural concerns, the complexity is an active developer pain point: in State of JS 2025, “Managing Dependencies” was the 3rd biggest pain point, and “Build tools” were 6th.

According to recent reports, however, getting rid of build tools is not the goal. Some use cases should not be handled by the browser, so bundlers and build tools will always have a role to play. The goal is making them lighter, composable, and less essential.

Nudeps1Which you can choose to read as either nude deps or nu (fresh) deps is a new kind of lightweight build tool that lets you continue using npm install to manage dependencies, vendor them locally, and import them via bare specifiers (package names like "vue" or @floating-ui/dom instead of URLs), without the bundler. (Related: How to train a upcoming language model from scratch usi...)

According to recent reports, you set it up once, and then you can forget about it: you keep npm installing packages and importing them by name, and they work in the browser. And it only ever touches your dependencies, never your own code.

Since my apprentice Dmitry and I prototyped the initial MVP in February, we and others have tested it on a variety of projects, and at this point I’m confident that — while not perfect — it’s ready for prime time. (Related: Showcase Your Projects in Spaces using Gradio...)

A core architectural difference between Nudeps and bundlers is that your own code remains untouched. In fact, it doesn’t even need a watcher that runs whenever you make edits! It only touches dependency files, and doesn’t rewrite anything, making it extremely lightweight in terms of complexity it adds.

Sources indicate that this means it can complement any other tooling — or none. You write raw HTML, CSS, JS? This is for you. You use a templating engine, a CSS preprocessor, and TypeScript? This is also for you (though understandably you may have less use for it). This also makes it complement static site generators and island architectures particularly well.

In a recent development, does it replace your build process? If all you needed it for was getting imports to work, it could. If you also compile your code (JSX, TypeScript, single-file components), you still need a tool for that, but it can be a much smaller one.

Bundlers make complex things possible. Nudeps is hoping to occupy the space on the left of the curve and make simple things easy.

Sources indicate that import maps allow us to import bare specifiers (package names like "vue") instead of URLs in the browser and are Baseline Widely Available. JSPM is a library that traces a dependency graph and generates an import map. It focuses on CDN use cases, but its engine is exposed as a separate library that can be repurposed, which is what Nudeps uses under the hood (with a lot of tweaks).

Import maps currently have to be inline in the HTML of every page, which would require templating, but external import maps can be easily emulated via a small script that injects the map.

Package managers like npm already give you the file structure and let you manage versioning, that structure just can’t be deployed as-is to the web.

Also, since Nudeps doesn’t bundle, packages with a lot of tiny modules pulled together by ESM imports may be slower to load initially. If you’re a package author that wants to provide a Nudeps-friendly bundle, generating a bundle that consolidates them somewhat can improve performance. But there is a tradeoff to all bundling: the more files are bundled, the less granularly they can be loaded. There is typically a sweet spot, and that varies depending on the structure and usage patterns of your package. But please do not bundle your package’s dependencies in there as well — these need to remain separate, so they can be shared with other packages that use the same version of the same dependency.

Nudeps is just the beginning, and is far from perfect. There are certainly plenty of unknown unknowns, and many things we simply haven’t gotten around to.

Besides bugfixes and closing the gaps above, at the top of the roadmap is testing more packages to ensure compatibility and uncover edge cases.

If you want to give Nudeps a try, the easiest way is to head to your terminal and run npx nudeps install in your project directory — or just let your agent do it.

I’m hoping that Nudeps is the first step towards a future of lighter, composable build tools. Try it and let us know how it went!

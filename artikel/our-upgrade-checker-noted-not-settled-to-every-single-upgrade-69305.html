We built a button that notes "this upgrade doesn't break your code." Then we fed it 300 real upgrade pull requests, and for the first 455 moves it mentioned the same thing every time: not settled.

Not "safe." Not "broken." Just a polite shrug, 455 times in a row.

That was the morning of Nov 22, 2026, the day we shipped upgrade receipts at Since. This is the story of why the shrug was partly a bug, partly the truth, and why we kept the truth.

Every developer has stared at a Dependabot-style bump and thought: will this break me? The changelog is long, the tests are green, and you merge on vibes.

Recent findings suggest that search can't answer that question, because the answer depends on your code. So we built one that does. You give Since your code and the version you want to move to, and it answers with one of three verdicts:. (Related: Breaking: Hyperparameter Search with Transformers and R...)

Sources indicate that the word "safe" is banned. A clear receipt states "nothing found in what was read," because that is the only honest sentence available. (Related: Sentence Transformers in the Hugging Face Hub...)

Look at the middle line. One release read only in part, and the whole move is not settled. That one strict word, "every," is the whole product. It is also the whole problem.

Launch day, we checked two boring, everyday moves: express 4.19.2 to 4.21.2, and zod 3.23.8 to 3.24.1.

Both came back not settled, each naming the releases we had read only in part.

Sources indicate that fine, we thought. Two popular packages, a few releases with thin notes. Bad luck.

So we measured how often "read in full" happens at all.

In a recent development, of the 41,298 release reads we had finished, 21.1% were read in full. By registry it looked like this:.

If you want a clear receipt, every release of the move has to be in that first bucket. An upgrade that crosses five npm releases at 16.4% each is, statistically, a coin that keeps landing on its edge.

Recent findings suggest that why is npm so low? The most common reason a release was only read in part was that its types extend a type from another package: 14,533 of the 14,927 partial npm reads said so. That looked like one fix away from a big jump.

In a recent development, it wasn't. Only 2,135 of them had nothing else missing. The rest were also missing the thing you'd think every release has: notes. No repository listed. A CHANGELOG.md with no section for that version. A releases page that stops after 5 pages. No publish date.

A lot of software ships with no explanation of what changed. We knew that in the abstract. Seeing it as a percentage was different.

Two verdicts on launch day is an anecdote. We wanted a real test, so we collected 300 upgrade-only pull requests from public repositories, npm and PyPI, at most 3 per repository: 260 where CI passed after the bump, and 40 where it broke (the head failed where the base had passed).

We had to throw out a lot to get there: 193 pull requests that changed more than dependencies, 450 from other registries or GitHub Actions bumps, 125 with no CI to compare against, and 53 whose base was already failing.

Then we ran the receipts. And the first 455 moves all noted not settled.

In a recent development, some of that was the honest 21% at work. Some of it was us.

Bug one: lockfile-only packages could never be cleared. 419 of those first 455 moves were indirect: packages that only the lockfile holds, pulled in by something else. Our code had no path for an indirect move to ever reach "clear." So it never did. Now an indirect move is read through what your packages actually call of it, and it rests on its own releases.

Bug two: "not settled" with no reason. A receipt where every release was read in full could still say not settled, with nothing after the colon, if some other package in the same check was still being read. The receipt was waiting on a stranger. Each move now stands on its own.

Recent findings suggest that bug three: the false clear we caught before it happened. This is the one that still makes me wince. A lockfile-only pull request sent no manifest, so a package your code declares directly was treated as indirect, and checked against what its dependents call instead of what your code calls. That is exactly how you get a "clear" that isn't. It hadn't fired yet. It was waiting. Now the manifest beside a changed lockfile is always read.

Sources indicate that bug four: one significant changelog sank the whole step. A changelog over 2 MB failed its read entirely. 367 steps had failed on it. Now it's read up to the cap, and the rest is named as not read.

That's the part I'd underline. Every one of these bugs pushed toward "not settled," except the third, which pushed toward a wrong "clear." A strict tool fails quiet and safe most of the time. The one bug that could make it loud and wrong is the one worth losing sleep over.

On the fixed harness, the first 44 pull requests gave us: 36 moves cleared, 3 whole pull requests clear, and no false clear.

Three out of 44. I'm not going to dress that up.

The ones still not settled split three ways: 135 moves whose releases were still being read, 111 with a release read only in part (mostly packages with native bindings, and JavaScript with no types, where the honest answer is "we'd have to read the package's code"), and 16 where no code imports the package at all.

In a recent development, the full replay isn't finished, so there's no published share yet. I'm telling you the interim numbers because the shape matters more than the total.

Here's the conversation every team building something like this has, usually with itself.

"What if we counted 'read in part' as good enough when the missing part is just types?".

"What if we cleared a move when the release notes don't mention anything that looks like your API?".

Industry observers note that either one would turn a lot of not settled into clear by tomorrow. Both would make "clear" mean less.

In a recent development, we didn't touch the definition. Instead we went after the reasons releases weren't read in full, at the source:.

In a recent development, after that last change, 8,793 of 43,192 finished reads were in full (20.4%, Nov 22, 6:35 AM). Of the first 31 releases read again, the "no section in the changelog" gap went from 14 to 4.

It's slow. Our public stats for the last 7 days, read this morning, show 2,928 releases read in full out of 15,705 (18.6%): 11,555 in part, 785 unreadable, 437 failed (since.dev stats, Nov 22, 9:34 AM MST). Every receipt we can't settle names what we didn't read.

Recent findings suggest that if you need an answer on every upgrade today, a strict "every release read in full" rule will frustrate you, and a looser tool that indicates "probably fine" will feel better. For a solo side project with good tests, your CI is honestly a fine receipt.

In a recent development, the strict rule earns its keep when someone downstream trusts the word "clear" without reading further: an agent deciding whether to merge, or a team that blocks merges on it. There, one false clear costs more than a thousand shrugs.

Sources indicate that A tool that answers "I don't know" most of the time is only useful if it tells you why, and if its "yes" is worth something. We'd rather ship 3 clear pull requests out of 44 that mean it than 40 that don't.

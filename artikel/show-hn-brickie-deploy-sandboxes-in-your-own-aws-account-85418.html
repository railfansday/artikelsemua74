📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Brickie lets you run durable sandboxes in your own cloud / k8s cluster.

Brickie sandboxes are built on top of agent-sandbox with custom snapshot/restore implemented on top of object storage. They are designed to be called from @hatchet-dev/sandbox and support the ability to take a coordinated snapshot of agent state. This means that every sandbox call is a retryable and observable Hatchet task. (Related: Breaking: Russia readying nuclear-armed satellite that ...)

It has been revealed that each sandbox session is a container with a shell and a workspace and runs in your Kubernetes cluster with flexible runtime support, including Kata, gVisor and AWS Nitro. Every call that changes the workspace produces a snapshot, which can be used to fork a fresh sandbox or resume an existing session.

Head over to the quickstart guide to get up and running your own Brickie sandboxes with a local Hatchet instance.

It has been revealed that brickie is in beta. Flags, chart values and the wire contract may change before 1.0. See the changelog. (Related: Industry News: Cat takes 37-mile train trip to London b...)

It has been revealed that under the hood, brickie uses the agent-sandbox controller and warm pools to run sandbox pods. On top of this, the Brickie provider does a few different things:.

Every brickie sandbox turn produces an immutable snapshot in your object store, keyed by sandbox and Hatchet run ID. These snapshots can be forked into new sandboxes, or used to resume an existing session. On agent-sandbox, state is persisted through a PVC per sandbox, which forces a cold start, while the only point-in-time snapshot is GKE-specific.

Every call is a Hatchet task, so it is retried, observable, and replayed from its own snapshot. A retried call finds the snapshot it already stored and does not run the command twice.

The same code path runs on a Docker engine, so the Kubernetes cluster is not needed for development locally.

It has been revealed that pull requests are welcome from vouched contributors, and the first ones should be small. CONTRIBUTING.md explains how to get vouched, what to work on first and how AI use is disclosed.

A three-field key built from the user agent stops routine auto-updates from reading as fresh devices — and the version string is the field you have to throw away.

In a recent development, caution — use it at your own risk. A user agent is user-controlled text. This is a coarse, spoofable hint for analytics and benign personalization, not authentication, fraud prevention, or a unique-person identifier. Track people only with informed consent, check the privacy rules that apply to you (including ePrivacy/GDPR and CCPA-style laws), and treat every fingerprint as an approximation. Most days this works. Then Chrome moves from 120.0.0.0 to 121.0.0.0 in the background, and the same laptop on the same network produces a fresh string:.

One patch release becomes a support ticket. A macOS point release does the same thing. A browser that changes its UA format does it to everyone at once.

Three fixes come to mind, and each one moves the problem.

You need one key that stays the same through routine updates and still differs when the browser or platform actually changes, and every string-level trick either keeps the noise or throws away the signal.

The shape of the fix is to let a parser split the string, then build the key from only the parts that identify a class of device:.

deviceFingerprint is a thin wrapper that returns just .fingerprint for callers that do not need the display fields.

Think of a library card stamped with the branch, the section, and the format — never the checkout date.

It has been revealed that two consequences. First, two people with the same card look identical; that is the cost of a stable class. Second, the version is not lost — it is still on the parsed object if you need it for display, but it stays out of the key.

The checkout date tells you when; the stamps tell you who.

It has been revealed that this is written against ua-parser-js 2.x (^2.0.10) and Vitest. The parser ships lookup tables, so pin the major version and re-run this test file when you bump it; a newly introduced detection rule can change a name and therefore your key.

Your buckets are Chrome|Windows|unknown instead of a long tail of patch versions, so a graph of "devices this week" does not spike every time a browser auto-updates.

Recent findings suggest that the comparison uses the stable key, while the email uses the friendly fields from the same parse. Chrome 120 to 121 is silent; a switch from Windows Chrome to macOS Safari is not.

Every optional field is normalized to null, so a missing device type never leaks the literal string "undefined" into a log or a UI.

When a parser upgrade changes a detection rule, this test fails before your analytics buckets split in production.

Sources indicate that read the caution at the top before you ship this. Reach for it only when all three are true:.

The smell test: if two different people with the same laptop setup would break your feature, this utility is the wrong tool.

Recent findings suggest that parsing is delegated, not hand-rolled. UAParser(userAgent) returns { browser, os, device }. Writing your own regex puts you in the business of tracking every vendor's UA format; the library owns that table. The cost is a dependency and its parse tables at module load.

Recent findings suggest that missing fields become null, not undefined. browser.name ?? null, os.name ?? null, and device.type ?? null give callers one predictable empty value. That matters when the result crosses a serialization boundary: JSON.stringify drops undefined properties but keeps null ones, so the shape stays identical.

Sources indicate that the key is three fields joined by |. Versions are deliberately absent. The unknown sentinel keeps the arity: a Windows Chrome desktop is Chrome|Windows|unknown, never the shorter Chrome|Windows, so a later device-type detection cannot silently reshuffle your buckets. The separator is for humans reading logs, not for security.

Industry observers note that deviceFingerprint is a one-line wrapper. Callers that only need the key can import one function; callers that need the label use parseUserAgent. Both paths run the same parse, so they cannot disagree.

Industry observers note that the cost is one parse and a few strings per call. There is no cache, no timer, and no retained reference: the UA string is borrowed for the call, three fields are normalized, and one joined string is allocated. Call it once per request or render and pass the result around instead of re-parsing in a loop.

Sources indicate that the discarded render is the reason this is a pure function: a render that is thrown away computes a string nobody uses, and a committed render computes the same string again. No effect, no cleanup, no ordering bug.

Server-rendering note. On the server the string comes from the {% raw %}user-agent header; in the browser it comes from navigator.userAgent. Those are not guaranteed to match. Chromium's User-Agent Reduction freezes much of the version detail and moves it to Client Hints, so a client-side parse can return unknown where a server-side header still has detail, and mobile detection can vary. Pick one side as the source of truth for your keys and use it consistently.

It has been revealed that compared to built-ins. navigator.userAgentData (Client Hints) gives structured brands, platform, and mobile fields, but it is Chromium-only, needs a secure context, and server access requires an Accept-CH opt-in. It also carries version detail that this utility intentionally discards, so it does not buy stability for this use case. No built-in gives a stable, cross-browser device-class string; the library is doing the normalization work, and the three-field key is what makes the result boring enough to store.

In a recent development, the trade is stability bought by throwing information away. You give up versions and uniqueness, and in return a routine revision stops looking like a new device.

According to recent reports, this belongs in coarse analytics and benign personalization. When you need to know who is at the door, the boring answer — a consented first-party id or a real session — wins every time. And use this at your own risk: it is a hint, not an identity.

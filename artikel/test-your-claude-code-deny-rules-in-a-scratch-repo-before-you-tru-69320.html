It has been revealed that most advice on making Claude Code safer states "write deny rules". I'm Denys, a Forward Deployed Engineer. Written with AI assistance, checked by me. I think the advice is right and incomplete, because a rule you never tried to get around is a guess. Here is how I would test one.

Anthropic's permissions page says rules are enforced by Claude Code and not by the model, and that instructions in CLAUDE.md don't change what the agent is allowed to do. It also says a rule matches the command text, so git -C . push is not matched by a rule for git push. (Related: How to train a new language model from scratch using Tr...)

Recent findings suggest that A public GitHub concern (#39459) reports the same thing in practice. With Bash(rm *) denied, the agent deleted the file with a Python one-liner. I am quoting the docs and that report here. I did not rerun them for this post, which is exactly why you should run yours. (Related: Few-shot learning in practice: GPT-Neo and the 🤗 Accele...)

Sources indicate that I sorted 93 public incident reports by cause in Is Claude Code safe? What 93 incident reports show, and the rule bypass was one of five patterns. This post is the method for finding out whether you have it.

Use a folder with nothing in it you care about, and a bare repo in a temp folder as the fake remote.

Nothing here touches a real project, and if a test goes wrong the damage is one temp folder.

Recent findings suggest that for each rule, state the goal in plain words and let the agent pick the route. Don't type the denied command yourself, because that tests nothing.

It has been revealed that write down each result in three columns: goal, route used, blocked or not. Whatever got through, you now know.

I would also try routes I have no result for: a command wrapped in bash -c, or one run through a package script. I don't know how any of them behave on your version. That is the point of trying.

A deny rule judges text, so for routes that text rules can't see, add one PreToolUse hook that looks at the whole command and blocks the five that would hurt you most. Keep in mind that a hook runs with your full access, and so does anything the sandbox doesn't cover. The docs say the sandbox is off by default and covers shell commands only.

For what no rule catches, git and backups are the layer that always works. Commit before you start, and keep production credentials out of the agent's folder.

Rules and tools change. Keep the scratch repo, keep the three columns in a file, and rerun the list after an upgrade or after you edit your rules. If a leak you closed reopens, you will see it the same day.

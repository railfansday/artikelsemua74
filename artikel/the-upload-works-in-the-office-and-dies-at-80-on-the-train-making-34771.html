The bug: owners attach a video or a batch of photos, the progress bar gets most of the way, and then the upload fails and starts again from zero. On office Wi-Fi it never happens. On a phone it happens a lot, because a long upload on a mobile network is very likely to hit at least one of these: a network switch (Wi-Fi to cellular), a dead zone, the user leaving the app, or a timeout somewhere between the phone and your server.

It has been revealed that A single POST with the whole file in the body has no way to recover from any of them. Here's what does.

Before changing the client, check the path the upload takes. A few limits are hit only by large or slow uploads, and they look like network failures from the phone:. (Related: Tech Report: The Reformer - Pushing the limits of langu...)

According to recent reports, test by uploading a file just over each limit from a fast connection. If that fails, the problem isn't the mobile network.

According to recent reports, on iOS, URLSessionConfiguration.timeoutIntervalForRequest (default 60 s) is an idle timeout: it fires when no data moves for that long, not when the whole request takes longer than 60 s. timeoutIntervalForResource (default 7 days) is the total limit. Setting the request timeout to a few minutes "because uploads are slow" mostly delays the error. Leave it, and make the upload resumable instead.

On Android with OkHttp, writeTimeout is also per write, not for the whole body. callTimeout is the total, and it's off by default. If someone set callTimeout to 30 seconds for the whole app, every upload that takes longer than 30 seconds fails, and that only happens on slow networks. The fix that actually solves it: upload in pieces, and let the client ask the server how much it already has.

Recent findings suggest that you don't need to design this yourself. Common options:.

Whatever you use, the client has to store the upload ID and the part list on disk, not in memory, so it can continue after the app is killed.

Industry observers note that iOS: use a background URLSession (URLSessionConfiguration.background(withIdentifier:)) with uploadTask(with:fromFile:). Background sessions only upload from files, so write the data (or each part) to a file first. The system carries on with the upload while your app is suspended or terminated by the system, and relaunches the app in the background when it's done. (If the user force-quits the app, iOS cancels its background transfers, which is another reason to keep the upload state on disk and resume on the next launch.) Implement application(_:handleEventsForBackgroundURLSession:completionHandler:) and call the completion handler after processing the events. Each part of a multipart upload can be its own background upload task.

Android: use WorkManager with a NetworkType.CONNECTED constraint so the work waits for a network and retries with backoff. For long uploads the user started, run it as a foreground worker with a progress notification (setForeground); on Android 14 and later that foreground service needs the dataSync type declared. Android 14 also added user-initiated data transfer jobs in JobScheduler, made for exactly this case.

The cheapest fix: a 12-megapixel photo doesn't need to go up at full size if the server shrinks it anyway. Resize and recompress on the device first. For video, check whether the server transcodes it anyway, and if it does, upload a lower bitrate version.

ToolJet OAuth Email Match Turns SSO Into an Account Takeover Path

🌐 Source: Dev • 📅 27 Nov 2026 • ⏱️ 4 min read (822 words, 📚 Deep Dive)
💡 Key Takeaways
  • Industry observers note that toolJet's OAuth SSO implementation once treated an email address as enough to identify an account.
  • ToolJet's GitHub advisory explains that SSO sign-in looked up an account by email.
  • Industry observers note that A caller who reached the public SSO callback with a trusted-issuer token for a victim's email could receive that user's ToolJet session.
📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that toolJet's OAuth SSO implementation once treated an email address as enough to identify an account. That design choice is the core of CVE-2026-137536, an authentication bypass that can give an unauthenticated caller a session for an existing user, including an administrator. The vendor advisory and CVE assignment describe the same failure: identity resolution depended on the provider-asserted email rather than a stored binding between the provider subject and the ToolJet account.

ToolJet's GitHub advisory explains that SSO sign-in looked up an account by email. The immutable SSO subject was checked for presence but was not stored as a user identity or used as the lookup key. The Google and Git strategies therefore had no durable (provider, subject) mapping to compare against the user being accessed. (Related: Steam is pitting 10 years of Game of the Year winners a...)

Industry observers note that A caller who reached the public SSO callback with a trusted-issuer token for a victim's email could receive that user's ToolJet session. The victim did not need to approve a prompt or supply a password. The same problem applied to local password users and invited users because the SSO path minted a session from the matched account rather than validating the original login method. Recent findings suggest that the vulnerable sequence was straightforward. ToolJet received an OAuth token, validated the provider response, extracted an email, and called a user lookup by email. If an account existed, ToolJet generated the session payload for that account.

In a recent development, the critical gap came before that lookup. A stable provider subject identifies an OAuth identity across email changes and account-linking events. ToolJet parsed the subject but did not bind it to the local user. An email match therefore became the de facto account link, even when the SSO identity had never been attached to that account.

Industry observers note that the advisory also notes that the server did not require a positive verified-email signal before linking or logging in. For Google, the vulnerable code ignored email_verified. For Git, the flow selected a primary address without requiring a verified result. The patched source at v3.21.94-beta adds an email-verification check before an SSO response can continue to account linking or session creation.

In a recent development, the exploit is not a universal password bypass for every ToolJet deployment. Several conditions still need to line up:.

Industry observers note that those constraints explain why the vendor advisory assigns a moderate self-assessed score while the CVE assigning organization rates the problem much higher. The vendor advisory uses a conditional attack-complexity score of 6.5. The CVE record carries CVSS 4.0 score 9.3 and CVSS 3.1 score 9.8. Both assessments agree that a successful match can produce full account control; they differ on how readily an attacker can obtain the required assertion.

Sources indicate that the bypass crosses the boundary between SSO and local authentication. A victim can have a strong local password, but the SSO callback does not consult it. If the application issues a session after matching the asserted email, the password becomes irrelevant to that path.

The same issue affects the practical value of MFA when the application treats the SSO assertion as sufficient authentication. ToolJet's advisory says the victim's password and password-based two-factor authentication are bypassed because authentication is decided by the asserted email. Responders should inspect the actual SSO and session logs instead of assuming that a protected local login prevents this class of takeover.

Industry observers note that the GitHub advisory lists versions before 3.21.94-beta as affected and versions at or above 3.21.96-LTS as patched. The CVE record lists the affected range from 0 up to, but excluding, 3.21.94-beta, with 3.21.94-beta marked fixed. ToolJet's 3.21.94-beta release notes include the SSO sign-in hardening from pull request 17960.

According to recent reports, that creates a beta and LTS distinction rather than a contradiction. 3.21.94-beta contains the upcoming checks, while 3.21.96-LTS is the patched stable LTS build named by the advisory. Operators should choose a supported release line, verify the exact build, and avoid treating a similar-looking version string as proof of the fix.

A prior ZoomEye verification for this topic returned 689 matches for app="ToolJet" and zero matches for vul.cve="CVE-2026-137536". The 689 figure is a product-fingerprint count, not a count of confirmed vulnerable ToolJet deployments. It demonstrates that ToolJet instances are discoverable on the internet, but it does not prove exposure, configuration, version, or exploitation.

In a recent development, upgrade to 3.21.94-beta or later on the beta line, or to 3.21.96-LTS or later on the stable LTS line. After upgrading, verify the running build and confirm that Google or Git SSO rejects a response without a positive verified-email result.

Review existing SSO configuration for restricted domains and the intended set of identity providers. Shared single-tenant issuers and self-asserted email flows deserve particular attention. Administrators should also check recent SSO callback records for sessions created from an email that had no prior (provider, subject) binding, especially sessions for privileged accounts.

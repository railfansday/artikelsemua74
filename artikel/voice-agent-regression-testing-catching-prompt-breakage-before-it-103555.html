Voice Agent Regression Testing: Catching Prompt Breakage Before It Ships

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Voice agent prompts are code. They control what the agent claims, when it moves between states, and what it refuses to do. But prompt changes rarely get the testing code changes get. Someone edits a system prompt, makes a few test calls by hand, and ships it. If it broke something, you usually find out from a customer.

Earlier posts covered running voicetest in GitHub Actions and how the LLM judges score. This one is about the workflow around them: which tests to write, how to word metrics so a regression actually fails them, and what to do when one does. None of these show up in a code review of the prompt diff, and voice agents don't produce the same conversation twice, so you can't assert on exact output. You need tests that check intent.

In a recent development, the most valuable regression tests are the ones written from real failures. When a bug report comes in, write the test that reproduces it before touching the prompt. Then fix the prompt until the test passes. The test stays in the suite, and that bug can't come back unnoticed.

A metric that passes no matter what the agent does is worse than no metric, because it makes the suite look healthier than it is. Weak metrics share a few habits:.

Industry observers note that strong metrics name something observable in the transcript. They state order when order matters ("before discussing"), and they describe what the caller experiences, not what the agent intended. The judge splits a metric into separate requirements and scores the fraction met, quoting the transcript as evidence. A metric with three clear requirements produces a score you can act on. A vague one produces a confident 0.9.

In a recent development, some regressions don't show up in the words at all. The agent might skip a tool call, collect the wrong keypad digits, or move to a node too early. By default the judge reads a plain transcript, which leaves those out. Set the judge input to events:.

It has been revealed that the judge then gets a timeline of speech, keypad input, tool calls, and node transitions, with timing when it's known. Metrics like "Agent looked up the order before quoting a delivery date" become checkable.

Industry observers note that synthetic tests only cover the scenarios someone thought to write. Production traffic covers the rest. Voicetest can import real call transcripts and replay them against the agent's current graph, so a prompt change is checked against yesterday's actual calls, not only the ones you wrote by hand. Use both: hand-written tests for the behavior you know matters, and replays for the cases you haven't thought of.

Here's a real one. We took voicetest's demo agent, a medical receptionist, and made two edits that each look reasonable on their own. We added a shortcut from the greeting straight to appointments for callers who "just want to check the time", to save them a step. And we rewrote the general prompt to sound warmer, which quietly dropped its "always verify patient identity" sentence.

A cooperative caller didn't catch it: the agent still asked for a date of birth out of common sense. A caller who declines to give one did:.

When the cause isn't that obvious, the Diagnose button on a failed result (or voicetest diagnose on the CLI) reads the graph, the transcript, and the failed metric, and points to where the graph went wrong:.

In a recent development, both of the fault locations are right. It also proposes a fix for each, as a diff:.

Apply & Test applies the change and reruns the test. On the CLI, --auto-fix does the same in a loop until the test passes or it hits an iteration cap. Treat the result like any other generated code, though. Here, the prompt fix is sound, but the transition fix just adds a condition to a shortcut that shouldn't exist. The better fix is deleting the edge. Review the diff, then rerun the full suite to make sure the fix didn't break a neighboring test. The diagnose recipe covers the options.

Everything above ran locally, against Qwen3 8B through llama.cpp, playing the agent, the caller, and the judge.

Industry observers note that every bug becomes a test. Every metric names something observable. Every prompt change runs the suite, real calls included. Every failure points to a node. None of it makes voice agents deterministic, but it means a prompt edit that breaks something gets caught before customers hear it.

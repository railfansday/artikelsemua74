In a recent development, when an app scales to zero, whatever it kept only on its own machine is lost, such as files written to local disk or /tmp and sessions held in memory, and timers or background loops meant to run between requests stop. Anything in a database, in object storage or in the platform's crons and queues keeps working, because it lives outside the instance. On Gregale, every wake starts from the same snapshot and parking discards the instance's local state, so Gregale looks for the usual mistakes: it refuses stateful base images and VOLUME directives when it accepts a deploy, and records an audit row the first time an app writes to a database-shaped directory such as /data or /var/lib/postgresql. These stateless contract checks are generally available on every blueprint. (Related: Electronics manufacturers set up memory 'war rooms' to ...)

By default the snapshot is taken from the deployment, right after the app becomes ready, not from the instance that parked. So every wake starts from the same state, whatever the last instance did, and two instances restored at once start from the same memory. Gregale rejects a stateful base image when it accepts the deployment, with stateless_only_violation and HTTP 422: postgres:16, mysql:8, redis:7, mongo:7, mariadb, cockroach, cassandra, clickhouse and the rest. A source tarball with a VOLUME directive, or with top-level data/ or db/ directories, is rejected for the same reason.

Gregale watches the state-shaped directories in every instance: data/ and db/ under the app's working directory, plus /data, /db and /var/lib/postgresql, /var/lib/mysql, /var/lib/redis and the data directories of other databases. The first write to each file there records one stateless.advisory audit row. The check is advisory: the app keeps running, and the row is your signal that the data will not survive the next park.

It has been revealed that the first command lists recent rows; the second streams them live while you exercise the app. Each file is reported once per instance, and an instance reports at most 256 files.

Warm snapshots. Pro and Scale apps can opt in to a second snapshot, taken when an instance parks after it has served a few requests. It is reused by every later wake and every instance until the next deploy, and it carries whatever those first requests left in memory: sessions, caches, rate-limit counters, per-user data and files under /tmp. After a restore, and after it has repaired the guest's clock and entropy, Gregale sends one POST to that path on the app's loopback listener. A 2xx answer lets the instance serve; a timeout or any other status discards it and Gregale cold-boots a fresh one instead. The timeout is 500 ms by default and at most 2 seconds. Check for a loopback peer and the X-Faas-After-Restore: 1 header in the handler: Gregale strips inbound x-faas-* headers at its public proxy, so a public caller cannot fake that marker. To close the connection before the snapshot is taken instead, add a before_checkpoint hook the same way. Redeploy after changing either: existing snapshots keep the configuration of the deployment that made them.

A Node or Python function declares the same thing as hooks in its handler file: init, beforeSnapshot and afterRestore (before_snapshot and after_restore in Python).

What is lost when an app scales to zero?

Anything kept only on the instance: files written to local disk or /tmp, sessions and caches held in memory, and timers meant to run between requests. Data in a database, object storage or the platform’s crons and queues is kept.

How does Gregale warn me that my app writes data it will lose?

It rejects stateful base images such as postgres:16 and VOLUME directives at deploy with stateless_only_violation, and records a stateless.advisory audit row the first time an app writes to a database-shaped directory such as /data or /var/lib/postgresql.

How do I reconnect to my database after a snapshot restore?

Declare an after_restore hook in gregale.yaml. Gregale sends one POST to that path on the app’s loopback listener after repairing the clock and entropy; a 2xx answer lets the instance serve, anything else falls back to a cold boot.

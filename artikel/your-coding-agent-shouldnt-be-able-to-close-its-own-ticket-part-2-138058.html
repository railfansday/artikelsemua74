What's a claim worth if the code has moved on since it was made?

That's not my question. It came from the comments on part one, and it was a better question than anything I'd asked in the post itself. 🙌.

Quick recap if you missed it. Part one argued that a coding agent should be able to claim a ticket is done, with evidence, but never decide it. A CI check or a named person decides. The agent keeps all its speed; it just doesn't mark its own work.

Industry observers note that the comments agreed with the split, and then politely took it apart at the edges. This post is about those edges, and what got built because of them. (Related: Industry News: The Partnership: Amazon SageMaker and Hu...)

Two commenters shaped this post, so they go first.

In a recent development, glenn left three comments, and each one turned into a change. The first: tie every completion claim to the exact commit it was made against, or the approval ends up attached to stale evidence. The last: the same permission boundary should cover the checks, because an agent that can edit the CI config can weaken the very thing that judges it.

Recent findings suggest that gautam K put the principle more sharply than I did: the ticket can only close when something the agent can't edit confirms it. The agent can propose Done. Only that check, or a person, can move it.

So now every claim is pinned to a commit. When a coding agent claims a criterion, Arbituro records the commit the job's branch or pull request stood at right then.

Sources indicate that the vital part: the agent doesn't send that commit. Arbituro reads it from the job's link, which only GitHub's own events move. An agent can't leave it out, and it can't name a convenient one. A commit the agent reports would just be more testimony. A commit GitHub reports is a fact. 🔒.

In a recent development, when more code lands after the claim, the person deciding sees it right next to the claim, in plain words: "2 commits pushed since". After a force push it says "The branch was rewritten since the claim" instead.

And opening the claim shows what GitHub recorded after it, oldest first: each check that reported and the commit it ran on, each commit pushed with its subject and the first files it touched, and the merge. You don't have to go and dig through GitHub to find out what "2 commits" means.

This was the real design question, and I went back and forth on it.

Withdrawing the claim automatically sounds safer. But agents push constantly, and plenty of pushes don't touch what was claimed. A fix to a typo in the README shouldn't throw away a claim about checkout. Auto-withdrawing would mean the person deciding never sees most claims at all.

Recent findings suggest that so a moved head warns and never withdraws. The claim stays there to decide. The person can still press Met, or press "Ask it to check again", which leaves a note on the job for the agent, under their own name. The agent reads it the next time it opens the job:.

In a recent development, one more honesty detail I care about: the wording always indicates "since the claim", never "since the agent checked". Arbituro knows where the branch stood when the claim arrived. It doesn't know exactly what the agent looked at. The screen shouldn't pretend it does. 🧐.

The same logic applies to CI, and this one is stricter.

Recent findings suggest that A check's pass is only true of the commit it ran on. So when a upcoming commit lands on the pull request, any criterion a named check had already passed goes back to undecided until that check reports again on the new commit.

No warning this time, a reset. Why the difference? A person's judgement might survive a small push; they can look and decide. A check's pass is a statement about one exact commit, and nothing else. What happened (the job's history) records which criterion was reopened, by which check, and both commits.

Claims can also carry screenshots now, for anything a screen proves. "Works on mobile" with an actual phone-sized screenshot beats "works on mobile" with a ✅. 📱.

Glenn's last comment is the one I keep thinking about.

Recent findings suggest that taking "close the ticket" away from the agent doesn't help much if the same pull request can quietly change what "passing" means. Edit the workflow so the test job skips the slow suite. Loosen CODEOWNERS. The check goes green, the criterion ticks, and everything looks verified. ✅ 🙃.

Two things are true in Arbituro now.

Agents running inside Arbituro can't write under .github at all. That covers workflows, the actions they call, and CODEOWNERS. It's enforced in code, on the files about to be pushed, not in a prompt. And a person still approves the change after that.

A coding agent in your own repo is different. Claude Code, Cursor and friends work in your checkout with your permissions. Arbituro can't stop them editing a workflow, and it shouldn't pretend to. That's what branch protection, required reviews and CODEOWNERS are for.

What Arbituro can do is make sure a weakened check never passes quietly. So before a named check ticks a criterion, Arbituro reads the pull request's changed files from GitHub. If any of them are under .github/, or a CODEOWNERS file, the criterion still ticks, but its line says so, in warning colour. Roughly:.

According to recent reports, the path links straight to the pull request's changed files on GitHub. The person signing the job off sees it at exactly the moment it matters.
